# Host interface — pins, load protocol, serial framing, readback contract

The host-facing spec. `PHASE1_CLOSEOUT_PART5.md` flagged that "the serial format
becomes host-facing spec: framing, bit order, and what happens when the host
stops reading" — this is that document, and it now also carries the **readback
contract** ruled after the byte-0 defect.

Everything here is observable at the pins. Nothing requires reading internal
state, which is what lets the same suite run against the gate-level netlist.

## Pins

`uio` carries everything that must be able to **stop driving** (inputs,
open-drain, tri-state); `uo_out` carries push-pull only. Both banks are exactly
full. The map is generated by `test/corpus.py` into `test/pinmap.vh` and checked
against `src/project.v`'s `MISO_PIN`/`CS_PIN` at generation time.

| pin | bank | lane | signal | class |
| --- | --- | --- | --- | --- |
| 0 | `uio[0]` | SPI-master | MISO | input |
| 1 | `uio[1]` | I²C | SCL | open-drain |
| 2 | `uio[2]` | I²C | SDA | open-drain |
| 3 | `uio[3]` | UART-rx | RX | input |
| 4 | `uio[4]` | SPI-target | SCLK | input |
| 5 | `uio[5]` | SPI-target | MOSI | input |
| 6 | `uio[6]` | SPI-target | CS | input |
| 7 | `uio[7]` | SPI-target | MISO | tri-state out |
| 8 | `uo_out[0]` | UART-tx | TX | push-pull |
| 9–11 | `uo_out[1:3]` | SPI-master | SCLK, MOSI, CS | push-pull |

`uo_out[6:4]` is the serial host view; `uo_out[7]` is spare and reads 0.

**Open-drain pins never drive a 1.** A pin's drive class follows the lane that
owns it (both its data pin and its clock pin), is fixed when the lane's header
loads, and is enforced at the output flop's D input — so an open-drain pin
driving high is unsatisfiable regardless of which opcode writes it. Low is
`oe = 1, out = 0`; the high phase is a **release** (`oe = 0`) and the line is
brought up by the bus pull-up, which is what makes an external device able to
hold SCL low and stretch the clock.

### Control inputs

| pin | name | meaning |
| --- | --- | --- |
| `ui_in[7]` | `prog` | 1 = load mode, 0 = run |
| `ui_in[6]` | `wr` / `push` | load: write strobe. run: TX payload PUSH. **Asynchronous** either way |
| `ui_in[5]` | `ptr` | load-pointer reset |
| `ui_in[4:1]` | `tx_nibble` | TX payload nibble, 2 pushes per byte (run mode) |

`wr` is treated as an asynchronous pin strobe: two flops to resolve
metastability and a third to see the edge. **Hold it for at least 3 clocks**, and
leave at least 3 clocks between writes.

## Loading a program

1. Assert `prog`.
2. Pulse `ptr` to reset the load pointer to 0.
3. For each byte: drive it on `uio[7:0]`, hold ≥3 clocks, raise `wr` for ≥3
   clocks, lower it, wait ≥3 clocks. The pointer auto-increments — there is no
   address bus.
4. Deassert `prog` to run.

### ⛔ Load the FULL store: all 256 bytes

The program store has **no reset**. A byte the host never wrote holds whatever
the SRAM powered up as, and a lane that ever reached one would execute it on a
real pin. So the chip **refuses to run until every store byte has been
written since power-on**:

* It counts **consecutive** writes; a `ptr` pulse restarts the count until 256
  have landed. Because the pointer auto-increments and wraps, 256 consecutive
  writes from any start cover every address. Once reached, the condition holds
  until `rst_n`.
* ⚠ **The full-store rule applies to the FIRST load after `rst_n`.** After
  that, partial reloads run: every byte is still defined, holding either the
  new program or the previous full load. The counter is a power-on guarantee,
  **not a per-load one**. A host that reloads part of the store is responsible
  for what the rest of it still holds.
* Until then the engine **does not run** (no dispatch, every pin released),
  including the window after reset if `prog` is low.
* **Deasserting `prog` before 256 consecutive writes sets CONFIG_ERR** (status
  bit 5, sticky until `rst_n`) so the host is told why the part is silent.

⇒ Write the program, then fill the rest of the store. The toolchain does this
for you: every image `pe_asm` / `pe_isa.write_image` emits is already 256 bytes,
the program followed by the **store filler** `FE FF C0` repeated (a parked,
non-driving `OP_REARM`).

Every `uio` pin is an **input** for the whole of load mode, which is what lets
the 8 protocol pins double as the load data port at zero pin cost. The 4
push-pull protocol outputs are held at **idle high** throughout, because
`uo_out` cannot release and an idling low could look like a START condition or a
clock edge to an attached device.

## The serial host view (`uo_out[6:4]`)

| bit | name |
| --- | --- |
| `uo_out[4]` | `data` |
| `uo_out[5]` | `strobe` |
| `uo_out[6]` | `valid` |

- `valid` is high for the whole of a frame and low between frames, so **its
  rising edge is the frame boundary**. Frame on that, not on a fixed stride.
- A frame is **12 strobed bits**: 8 payload bits **LSB first**, then a 3-bit
  **`kind`** field (LSB first), then the **marker** bit **last**.

  | marker | `kind` | the frame is |
  | --- | --- | --- |
  | `1` | 7 | **status** — the byte below |
  | `0` | `0..4` | **RX payload from that lane** |
  | `0` | 7 | **readback** byte (program store), not a lane |

- ⛔ **The marker arrives last**, so a host cannot use it to decide how many
  bits to read. Both frame types are therefore the **same width**; do not
  expect a short frame.
- One bit per two clocks; `strobe` is high for one clock per bit. Sample `data`
  while `strobe` is high.
- Payload and status frames **alternate**, so liveness is in the stream even
  when no payload is moving.

⭐ **Why `kind` exists.** The frame was 9 bits — 8 payload plus the marker —
which could not say *which lane* produced a received byte. With two receiving
lanes the host had to guess, which is the same failure the per-lane TX queues
exist to prevent, seen from the other direction. It also resolved a second
problem: a **readback** byte and an **RX payload** byte both carried
marker `0`, so the two were indistinguishable on the wire and were being told
apart by whichever mode the host believed it was in. `kind = 7` now says "not
a lane" explicitly.

### The status byte

| bit | meaning |
| --- | --- |
| 0 | always 1 — alive |
| 1 | TX underrun (sticky, per lane OR-ed) |
| 2 | RX overflow (sticky) |
| 3 | `ovr` (sticky) |
| 4 | **TX-full** — a push arrived on a full queue (sticky) |
| 5 | **CONFIG_ERR** — the program is illegal; the chip refused to run it |
| 6 | **RX-drop** — a payload arrived while one was still pending (sticky) |
| 7 | **CLOCK-STRETCH** — a clocked receive's consume point found no bit: the peer held the clock past the bus-fault bound (sticky) |

**Overflow is reported in the stream, never as a stall**, because a host that
has stopped reading cannot be told by a pin it is not reading.

### ⛔ CONFIG_ERR HALTS THE WHOLE ENGINE, not just the offending lane

An illegal action stops **every lane**, because `config_err` gates dispatch
engine-wide: `ST_IDLE` will not dispatch at all while it is set. This is
intended, and it is the same posture 1.6s already takes at LOAD time — a
program the chip refuses is refused in full.

**Why fail-stop rather than per-lane:** a program that contains one illegal
action is a program whose provenance is in doubt, and the other lanes are
driving *buses* — an I²C bus with other devices on it, an SPI target's
tri-state MISO. Continuing to drive them from a program that has already
been shown to be malformed is the wrong risk to take, and a host cannot tell
"the lane I care about is fine" from "the part is running a corrupted
image".

**What counts as illegal at load release:** leaving load mode before the whole
store was written (above). The engine never started, so no pin moved.

**What counts as illegal at run time:**

* a `SHIFT` lane whose clock pin **is** its data pin (1.6x) — the clock write
  would overwrite the data bit, emitting a well-formed frame of wrong data;
* a **self-clocked action with a zero bit count** — either a clocked
  `SHIFTIN` at `count = 0`, or a clocked `SHIFT` at `count = 15`, where
  `count + 1` wraps to zero in the 4-bit field.

⚠ **A host sees CONFIG_ERR and must assume the image, not one lane, is**
**suspect.** Reload before expecting anything else to run. The flag is
sticky and the engine does not resume on its own.

⭐ The refusal emits **no pin edges**: the drive arms are gated on the same
condition, so a refused action does not move a pin on its way to being
refused. `tb_pinrange +MODE=3` asserts exactly that, on both routes.

### How the flags clear, and what that costs you

**Reset only.** Every flag above is sticky until `rst_n`. There is no
clear-on-read. Stated plainly because it has a consequence a host must plan
around: **a single TX underrun makes the stream carry status frames in every
idle slot for the rest of the run.**

That is bounded rather than harmful, and the two reasons are worth knowing:

- **A payload always wins the next frame slot.** Self-started status is queued
  only when no RX payload is pending, so a set flag can never push data out of
  the stream — it fills slots the payload did not want.
- **An RX payload is held one deep.** `rx_push` from the engine is a one-cycle
  pulse, so before this a payload arriving mid-frame was simply *lost*; with a
  set sticky flag filling idle slots that would have meant dropped bytes rather
  than delay. A second pulse arriving while one is pending is a real overrun
  and sets **RX-drop**.

  ⚠ **The margin here is smaller than it was described as.** This used to read
  "two orders of margin: a frame takes 18 cycles and the fastest RX lane
  delivers a byte every 414". The frame figure was wrong twice over — a frame
  is **25 cycles** (12 bits at two clocks, plus one clock to queue the next)
  and a **payload slot is 50**, because a status frame always follows a payload
  one. And the comparison was against the wrong quantity: what binds a one-deep
  register is not a lane's average byte period but whether **two completions
  from different lanes land inside one 50-cycle slot**, which is a question
  about their relative phase. The two RX lanes' byte periods are 400 and 3312
  cycles, unrelated, so the phase drifts and a collision is reachable.

  ⇒ **What is guaranteed is that a collision is reported, not that it cannot
  happen.** `test/run_rxbw.py` measures both halves: forced over-rate, 3,405
  bytes dropped with **RX-drop set every time and never silently**, and every
  surviving byte delivered **in order** — so the register refuses the new byte
  rather than clobbering the pending one. A host that must not lose a byte
  should keep the aggregate completion rate below one per 50 cycles and read
  **RX-drop**.

⛔ **Status does not self-start on a timer.** An unconditional heartbeat would
queue a frame every 25 cycles — it would have paid for liveness with the data
it exists to report. Status self-starts only while a flag is set, which is what
makes it an error channel rather than a background load.

### The link's real capacity

| | |
| --- | --- |
| bit time | 2 clocks |
| frame | 12 bits + 1 queue clock = **25 clocks** |
| payload slot | **50 clocks** (a payload frame and the status frame after it) |
| payload capacity | **8.00 Mb/s** |
| shipped two RX lanes | 1.12 Mb/s = **14.0% utilised** |
| readback, one byte | 50 clocks (readback frames alternate with status too) |
| readback, full 256-byte store | 12,800 clocks = **256 µs** at 50 MHz |

⚠ **Readback got slower with the frame**, and it is worth stating because a
host that polls the store after every load pays it: a full walk was 194.6 µs at
9 bits and is **256 µs** at 12. That is the honest cost of the lane field —
readback frames carry `kind = 7` and gain nothing from it, but the frame could
not widen for payload alone (the marker arrives last, so both types must be the
same width).

⛔ **`1.6p` published "2.2% of the clock" and that was the raw pin rate** — one
bit per clock on the data pin, which the stream never runs at. It ignored the
two-clock bit time, the 4 non-payload bits per frame, the status frame that
always follows a payload, and the queue clock between frames. ⚠ The error
**predates** the 12-bit frame: at 9 bits the true figure was 10.6%, and the
widening moved it to 14.0% — the mis-stated capacity accounted for the other
4.8×. Both numbers are measured by `test/run_rxbw.py`, which reproduces the
50-clock slot at every point of a 12-point sweep and locates the loss boundary
where the same arithmetic predicts it.

## The readback contract

In **load mode** the payload frames carry the program store, so a host can
verify what it loaded. In **run mode** they carry RX payload.

1. **Readback starts at address 0, and the first payload frame IS byte 0.**
2. **The rewind trigger is `rst_n`.** Not entering load mode: the stream runs
   *concurrently* with loading, so by the time the last byte is written the walk
   is already past the image. The program store is deliberately **unreset**, so
   a reset rewinds the walk and keeps the image.
3. **The stream is only meaningful once the load is complete.** Reading it during
   the load returns whatever has been written so far, and the walk may pass
   addresses before the host writes them.
4. Reading past the loaded region returns **X**, not 0 — the store is left
   uninitialised on purpose, so a program that reads past its end looks wrong
   rather than plausible.

⛔ **Points 1 and 2 are a ruling, not a description of an accident.** Byte 0 used
to be unreachable: the readback incremented its pointer in the same cycle it
requested a read, and the store was addressed from the incremented value, so
address 0 was never requested and the first frame carried a register from before
any read. Byte 0 is the first byte of lane 0's header — its `pin` and `clkpin`
fields — so the one byte a host could not verify was part of the descriptor
deciding which physical pin lane 0 drives.

The fix was two parts, and **the first alone was not enough**: latching the
pre-increment address made byte 0 reachable but it arrived *second*, behind one
stale frame, because a frame was still queued before its own read landed. The
readback now **primes** — its first two visits issue the read and let it land
without queueing a frame — so every frame carries the byte its own request
fetched. A pipeline's first output is not data.

## Supplying a payload byte — the TX nibble channel

| pin | run-mode use |
| --- | --- |
| `ui_in[4:1]` | TX payload nibble, **2 pushes per byte, HIGH nibble first** |
| `ui_in[6]` | TX payload **PUSH** (rising edge; it is `WR` in load mode) |

Push the high nibble, then the low nibble. The assembled byte enters a **2-deep
FIFO**; the engine pops one byte each time a lane's `SHIFT` consumes data. There
is **one** FIFO, not one per lane: the shift action already names its lane, so
the host pushes bytes and the program does the routing — the same trick that
deleted the address bus.

- **`uio` carries protocol pins only.** Nothing of the data channel is spent on
  it, which is what lets the host feed a lane while a protocol is live.
- **A push on a full FIFO is reported, never stalled** — sticky **TX-full** in
  the status frame (bit 4). The host has no back-pressure pin, so a flag in the
  stream is the only honest answer, the same reasoning as RX overflow.
- **A lane that consumes with the FIFO empty records an underrun** (status
  bit 1), per lane. Staging one byte ahead is what the FIFO is for.

⛔ **This section previously described something else, and that was a real
defect rather than loose wording.** The RTL took `host_data` from `uio_q1` —
*eight bits of the protocol bus* — and pushed on `ui_in[0]`, while `ui_in[4:1]`
sat in the `_unused` concatenation and no FIFO existed at all. Both halves of
F1's ruled channel (`PHASE1_CLOSEOUT_PART3`) were unbuilt, and the consequence
was not cosmetic: **a host could not deliver a payload byte without driving the
very pins a live protocol was using.** That is why no program could address the
SPI FRAM, and therefore why no I²C ACK — and no peer-driven clock stretch — was
reachable. Fixed; this document now describes the ruling rather than the
deviation.

⚠ PART4 superseded the **RX** half of that table (three spare `uo_out` pins
cannot carry a nibble plus a valid, so RX went bit-serial — the serial host view
above), and PART5 framed status **into** the stream, which retires the
`ui_in[5]` pop and the `ui_in[0]` view select. Neither supersedes the TX nibble
or "zero `uio` spent".
