# Host interface — pins, load protocol, serial framing, readback contract

The host-facing spec. `PHASE1_CLOSEOUT_PART5.md` flagged that "the serial format
becomes host-facing spec: framing, bit order, and what happens when the host
stops reading" — this is that document, and it now also carries the **readback
contract** ruled after the byte-0 defect.

Everything here is observable at the pins. Nothing requires reading internal
state, which is what lets the same suite run against the gate-level netlist.

## Pins

`uio` carries everything that must be able to **stop driving** (inputs,
open-drain, tri-state); `uo_out` carries push-pull only. Both banks are exactly
full. The map is generated by `test/corpus.py` into `test/pinmap.vh` and checked
against `src/project.v`'s `MISO_PIN`/`CS_PIN` at generation time.

| pin | bank | lane | signal | class |
| --- | --- | --- | --- | --- |
| 0 | `uio[0]` | SPI-master | MISO | input |
| 1 | `uio[1]` | I²C | SCL | open-drain |
| 2 | `uio[2]` | I²C | SDA | open-drain |
| 3 | `uio[3]` | UART-rx | RX | input |
| 4 | `uio[4]` | SPI-target | SCLK | input |
| 5 | `uio[5]` | SPI-target | MOSI | input |
| 6 | `uio[6]` | SPI-target | CS | input |
| 7 | `uio[7]` | SPI-target | MISO | tri-state out |
| 8 | `uo_out[0]` | UART-tx | TX | push-pull |
| 9–11 | `uo_out[1:3]` | SPI-master | SCLK, MOSI, CS | push-pull |

`uo_out[6:4]` is the serial host view; `uo_out[7]` is spare and reads 0.

**Open-drain pins never drive a 1.** A pin's drive class follows the lane that
owns it (both its data pin and its clock pin), is fixed when the lane's header
loads, and is enforced at the output flop's D input — so an open-drain pin
driving high is unsatisfiable regardless of which opcode writes it. Low is
`oe = 1, out = 0`; the high phase is a **release** (`oe = 0`) and the line is
brought up by the bus pull-up, which is what makes an external device able to
hold SCL low and stretch the clock.

### Control inputs

| pin | name | meaning |
| --- | --- | --- |
| `ui_in[7]` | `prog` | 1 = load mode, 0 = run |
| `ui_in[6]` | `wr` / `push` | load: write strobe. run: TX payload PUSH. **Asynchronous** either way |
| `ui_in[5]` | `ptr` / `tag[1]` | load: load-pointer reset. run: TX queue tag, high bit |
| `ui_in[4:1]` | `tx_nibble` | TX payload nibble, 2 pushes per byte (run mode) |
| `ui_in[0]` | `tag[0]` | run: TX queue tag, low bit |

`wr` is treated as an asynchronous pin strobe: two flops to resolve
metastability and a third to see the edge. **Hold it for at least 3 clocks**, and
leave at least 3 clocks between writes.

### Input synchronization and host timing

*Rulings CDC1–CDC3, silicon fixes #4 and #5.* Every host input is asynchronous
to the chip's clock. The host's microcontroller runs on its own clock, and TT
routes `clk` and `rst_n` "like any other input pins". So each input reaches
the logic in one of two ways:

| input | how it enters | latency `k` (cycles, 50 MHz) |
| --- | --- | --- |
| `rst_n` | asserts **immediately**; releases through a 2-flop reset synchronizer | release: k = 2 (40 ns) |
| `ena` | 2-flop synchronizer | k = 2 |
| `prog` (`ui_in[7]`) | 2-flop synchronizer | k = 2 |
| `ptr` (`ui_in[5]`, load mode) | 2-flop synchronizer | k = 2 |
| `wr` / `push` (`ui_in[6]`) | 3-flop synchronizer, edge detected after it | edge seen 2–3 cycles after the pad edge |
| `uio_in[7:0]` | 3-flop synchronizer (`pin_in` taken after 2) | 2 cycles |
| `tx_nibble`, `tag` (`ui_in[4:0]`, run mode) | **not synchronized**: sampled when the synchronized `wr` edge is detected | see the hold rule below |

The data pins are deliberately not synchronized bit by bit. A multi-bit value
passed through per-bit synchronizers can resolve each bit differently, so a
nibble changing near our clock edge could come out scrambled. Instead the
data is **qualified by the strobe**: the chip samples it only after the
synchronized `wr` edge, by which time the host's rules below guarantee it's
stable, so no data flop can go metastable.

**The host's rules, at 50 MHz:**

- **Data and tag hold:** `tx_nibble` and `tag` must be stable from **≥ 1 cycle
  (20 ns) before `wr` rises** until **≥ 4 cycles (80 ns) after it**. The chip
  samples on the cycle after the synchronized edge is detected. That's 3
  cycles after the pad edge, or 4 if the first synchronizer flop resolves
  late. This applies equally to the byte on `uio[7:0]` in load mode, which the
  load procedure's "hold ≥ 3 clocks" before `wr` and the 3-clock `wr` pulse
  already cover.
- **Level-control ordering:** `prog` and `ptr` must be stable **≥ 3 cycles
  (60 ns) before** the `wr` edge they qualify (their 2-flop synchronizer plus
  one) and stay stable until that edge has been taken, ≥ 4 cycles after it.
  Concretely: assert `prog`, wait ≥ 60 ns, then pulse `ptr` or begin writing;
  after the last byte, wait ≥ 80 ns before deasserting `prog`.
- **Pulse width:** `ptr` must be held for **≥ 3 cycles (60 ns)**, so its
  synchronizer is guaranteed to see it.
- **Reset:** after `rst_n` rises, the chip leaves reset 2 cycles (40 ns)
  later. Wait at least that long before the first `ptr` or `wr` edge. `prog`
  may already be asserted; it only has to meet the ordering rule above.

The demo board's microcontroller meets all of these with orders of magnitude
to spare, but they are the contract. The bench drivers (`host_feed.vh`, the
cocotb harness, gl_test) obey them.

⛔ **Before this fix,** `prog` and `ptr` fed core logic directly and `rst_n`
released every flop directly. A `prog` edge near our clock edge could leave
part of the engine running and part not, in the same cycle. Neither
simulation nor static timing can see that class of bug: the timing setup's
4 ns input delay assumes a synchronous host. It was found because the worst
timing path of a canary run started at a pin. `model/gate_cdc.py` now
checks the structure on every push (its must-fire, `M_CDC_RAW`, is the old
wiring, where `prog` alone reached 3,379 flop inputs).

## Loading a program

1. Assert `prog`.
2. Pulse `ptr` to reset the load pointer to 0.
3. For each byte: drive it on `uio[7:0]`, hold ≥3 clocks, raise `wr` for ≥3
   clocks, lower it, wait ≥3 clocks. The pointer auto-increments — there is no
   address bus.
4. Deassert `prog` to run.

### ⛔ Load the FULL store: all 256 bytes

The program store has **no reset**. A byte the host never wrote holds whatever
the SRAM powered up as, and a lane that ever reached one would execute it on a
real pin. So the chip **refuses to run until every store byte has been
written since power-on**:

* It counts **consecutive** writes; a `ptr` pulse restarts the count until 256
  have landed. Because the pointer auto-increments and wraps, 256 consecutive
  writes from any start cover every address. Once reached, the condition holds
  until `rst_n`.
* ⚠ **The full-store rule applies to the FIRST load after `rst_n`.** After
  that, partial reloads run: every byte is still defined, holding either the
  new program or the previous full load. The counter is a power-on guarantee,
  **not a per-load one**. A host that reloads part of the store is responsible
  for what the rest of it still holds.
* Until then the engine **does not run** (no dispatch, every pin released),
  including the window after reset if `prog` is low.
* **Deasserting `prog` before 256 consecutive writes sets CONFIG_ERR** (status
  bit 5, sticky until `rst_n`) so the host is told why the part is silent.

⇒ Write the program, then fill the rest of the store. The toolchain does this
for you: every image `pe_asm` / `pe_isa.write_image` emits is already 256 bytes,
the program followed by the **store filler** `FE FF C0` repeated (a parked,
non-driving `OP_REARM`).

Every `uio` pin is an **input** for the whole of load mode, which is what lets
the 8 protocol pins double as the load data port at zero pin cost. The 4
push-pull protocol outputs are held at **idle high** throughout, because
`uo_out` cannot release and an idling low could look like a START condition or a
clock edge to an attached device.

### ⛔ Isolate every `uio` peer during ANY load

Because `uio` **is the load data port**, a device wired to the `uio` protocol
pins sees the whole image as bus traffic during **every** program load — the
first one after power-up as well as any reload. **The host must electrically
isolate those peers for the duration of each load**, or they may see arbitrary
transactions.

- **Measured** (an I²C FRAM on `uio[1]`/`uio[2]`, each of the 29 tracked
  images loaded): **23 of 29 images produce START conditions** on the bus, up
  to **24** for `i2caddr_image`. None of them happened to clock out the
  FRAM's address after a START, so nothing was written — that is luck in the
  bit patterns, not a property: another image can address the part and write
  it. `test/run_reload.py` keeps a **harm demonstration** (the peer connected
  through a load) that prints what the peer saw; it is a measurement of this
  limit, never a pass.
- **Use a bidirectional bus switch, with its enable driven by the host**: a
  74CBT/CBTLV-class FET switch, or a TCA9548A-style I²C mux. ⚠ A one-way
  buffer (e.g. 74AHCT125) is not suitable for SDA, which is bidirectional.
  ⚠ **Do not isolate by powering the peer down**: driving the pins of an
  unpowered chip can back-power it through its input protection diodes.
- **Not affected:** peers on `uo_out` (UART-tx, SPI master). Load mode holds
  those pins idle-high.

### Reloading a program — a reload is a clean slate

A reload (PROG high, the image written, PROG low) is an **abort**: whatever a
lane was doing stops where it is. The chip guarantees what happens to its own
state and pins; what an aborted transaction means to a peer is the peer's.

**What clears** — the halt state equals the power-on reset state, by
construction (one register list, at the top of `src/pe_engine.v`, used by
both):

- every lane's program state, bit position, clocked-phase state, pending
  hold, arm, pin class (`pin_pp`, `pin_inv`) and header copy;
- **the TX queues** and a half-pushed byte, on the synchronized PROG rise.
  ⇒ **After a reload, TX starts with the first byte pushed after PROG
  falls.** A byte pushed before the reload is gone, even if no bit of it was
  sent;
- **a received byte not yet read** when PROG rises. ⇒ **Drain RX before
  raising PROG.**

**What is kept:** the sticky status flags — timeout, overflow, `CONFIG_ERR`,
clock-stretch, underrun. They are the host's to read after halting; only
`rst_n` clears them. What the host can learn from them:
- a timeout reaches the host as **status bit 3 (`ovr`)**, which every engine
  fault sets: a timeout reads as bit 3 with bits 5 and 7 clear, and once
  another fault has set, a timeout can't be distinguished. The per-lane
  `l_timeout` register is internal, with no host readout;
- underrun and overflow are reported **OR-ed across lanes** (bits 1 and 2), so
  the host learns *that* one happened, not *which lane*.

⚠ **Limitation:** the host cannot identify which lane timed out, underran or
overflowed.

**The pins at the halt:**

- `uio` pins release (`uio_oe` = 0).
- The four `uo_out` protocol outputs go idle-high in **two steps**: in the
  first PROG cycle every output **except a declared clock pin** (some lane's
  header `clkpin`) goes high; the clock pins follow one cycle later. So an
  SPI chip-select deasserts **at least one clock (20 ns) before** any SCK
  edge the halt causes, and no pad skew can let SCK clock a stale bit into
  the part.
- After PROG falls, no pad moves until the new program's first action: the
  pads sit at the reset idle, not at the halted program's last level. The
  header load and priming take 96 + 4R + S cycles before the first dispatch
  (see *Start-up* below), so nothing drives in that window.

**What an aborted transaction looks like to a peer** (measured by
`test/run_reload.py`):

| bus | at the abort | after the reload |
| --- | --- | --- |
| UART | a cut frame (no stop bit at its expected place) | frames from the first byte pushed after PROG fell |
| SPI master | CS rises first; the byte in flight is lost, not written | the next transaction runs clean |
| I²C | ⚠ releasing SCL from low **is** an SCL rise: the peer latches whatever is on SDA as the next bit, so a cut after 7 bits of a byte **completes that byte** with an arbitrary bit 8, and a FRAM may write it. **Reload an I²C lane between transactions.** | the next transaction runs clean (peer isolated during the load) |
| 1-Wire | the release shortens the low pulse in progress (an aborted slot) | the new program's reset pulse re-synchronizes the part; presence and the ROM read are exact |

**Known limits:**

- `rst_n` is asynchronous and forces all four `uo_out` outputs in the same
  cycle; the two-step order applies to a reload, not to a reset.
- On I²C, the order in which SDA and SCL rise at a release is decided by the
  bus pull-ups, not the chip.
- The `uio` isolation requirement above. ⭐ Fix candidate, not on this chip: a
  **bit-serial program load on `ui_in`**, so `uio` never carries load traffic.

### Start-up: from PROG released to the first dispatch

With the store fully written, the engine reaches its first dispatch a fixed
chain of steps after the PROG pad is sampled low, plus one term that depends on
the program:

| step | cycles (50 MHz) |
| --- | --- |
| PROG sampled low → engine run (`prog` 2-flop synchronizer) | 2 |
| engine reset releases (one flop, `eng_rst_n`) | 1 |
| header load: 1 + 3 × N_LANES × HDR_BYTES | 91 (5 lanes × 6 bytes) |
| priming: 4R + S + 1 | at most 42 |
| first dispatch | 1 |
| **total** | **96 + 4R + S**, and never more than **137** (2.74 µs) |

- **R**, the action slots filled before any lane is released: one head slot
  per lane, plus that lane's spare slot **unless the lane's first action is a
  chaining REARM** (level 0), whose successor is the head itself.
- **S**, idle cycles of the refill scan: each refill takes 4 cycles; a scan
  step that finds a lane with nothing to fetch costs 1. The scan serves the
  lane with the **smallest D_sched** first (ties to the lowest lane index),
  then goes round-robin from lane 0. S is 0 or 1 on every shipped image.
- Both are computable from the image alone, before loading it: the formula is
  the **exact** start-up of a given image.
- **The guarantee for any image is 137 cycles:** 4R + S is at most 41 (every
  lane is always live after the header load; R = 10 when no lane starts on a
  chaining REARM, and every winner and REARM pattern was enumerated). The
  shipped images span 120–137; that range describes them, it is not a bound.
- **A reload starts up exactly like a first load:** the same chain, measured
  on `test/run_reload.py`'s reload arms, including a reload into a different
  program.

The engine starts only on a program load: there is no start path at power-on.

## The serial host view (`uo_out[6:4]`)

| bit | name |
| --- | --- |
| `uo_out[4]` | `data` |
| `uo_out[5]` | `strobe` |
| `uo_out[6]` | `valid` |

- `valid` is high for the whole of a frame and low between frames, so **its
  rising edge is the frame boundary**. Frame on that, not on a fixed stride.
- A frame is **12 strobed bits**: 8 payload bits **LSB first**, then a 3-bit
  **`kind`** field (LSB first), then the **marker** bit **last**.

  | marker | `kind` | the frame is |
  | --- | --- | --- |
  | `1` | 7 | **status** — the byte below |
  | `0` | `0..4` | **RX payload from that lane** |
  | `0` | 7 | **readback** byte (program store), not a lane |

- ⛔ **The marker arrives last**, so a host cannot use it to decide how many
  bits to read. Both frame types are therefore the **same width**; do not
  expect a short frame.
- One bit per two clocks; `strobe` is high for one clock per bit. Sample `data`
  while `strobe` is high.
- Payload and status frames **alternate**. In run mode the stream carries a
  frame only when there is RX payload or a status flag set: **an idle chip is
  silent.**
- ⚠ **Limitation:** a host cannot tell an idle chip from a dead one through
  the stream. It can watch its own protocol pins for expected activity, or
  reload, which produces readback frames (at the cost of restarting the
  program).

⭐ **Why `kind` exists.** The frame was 9 bits — 8 payload plus the marker —
which could not say *which lane* produced a received byte. With two receiving
lanes the host had to guess, which is the same failure the per-lane TX queues
exist to prevent, seen from the other direction. It also resolved a second
problem: a **readback** byte and an **RX payload** byte both carried
marker `0`, so the two were indistinguishable on the wire and were being told
apart by whichever mode the host believed it was in. `kind = 7` now says "not
a lane" explicitly.

### The status byte

| bit | meaning |
| --- | --- |
| 0 | always 1 — alive |
| 1 | TX underrun (sticky, per lane OR-ed) |
| 2 | RX overflow (sticky) |
| 3 | `ovr` (sticky) |
| 4 | **TX-full** — a push arrived on a full queue (sticky) |
| 5 | **CONFIG_ERR** — the program is illegal; the chip refused to run it |
| 6 | **RX-drop** — a payload arrived while one was still pending (sticky) |
| 7 | **CLOCK-STRETCH** — a clocked receive's consume point found no bit: the peer held the clock past the bus-fault bound (sticky) |

**Overflow is reported in the stream, never as a stall**, because a host that
has stopped reading cannot be told by a pin it is not reading.

### ⛔ CONFIG_ERR HALTS THE WHOLE ENGINE, not just the offending lane

An illegal action stops **every lane**, because `config_err` gates dispatch
engine-wide: `ST_IDLE` will not dispatch at all while it is set. This is
intended, and it is the same posture 1.6s already takes at LOAD time — a
program the chip refuses is refused in full.

**Why fail-stop rather than per-lane:** a program that contains one illegal
action is a program whose provenance is in doubt, and the other lanes are
driving *buses* — an I²C bus with other devices on it, an SPI target's
tri-state MISO. Continuing to drive them from a program that has already
been shown to be malformed is the wrong risk to take, and a host cannot tell
"the lane I care about is fine" from "the part is running a corrupted
image".

**What counts as illegal at load release:** leaving load mode before the whole
store was written (above). The engine never started, so no pin moved.

**What counts as illegal at run time:**

* a `SHIFT` lane whose clock pin **is** its data pin (1.6x) — the clock write
  would overwrite the data bit, emitting a well-formed frame of wrong data;
* a **self-clocked action with a zero bit count** — either a clocked
  `SHIFTIN` at `count = 0`, or a clocked `SHIFT` at `count = 15`, where
  `count + 1` wraps to zero in the 4-bit field.

ⓘ **The UNCLOCKED forms are assembler-refused, silicon-defined (16-bit cycle
over an 8-bit register).** An unclocked `SHIFT` at `count = 15` or `SHIFTIN`
at `count = 0` is **not** CONFIG_ERR: the same 4-bit arithmetic wraps, so the
lane runs a 16-bit cycle over the 8-bit `l_tx` / `l_rx` register. That is
defined behaviour, but it is meaningless as a byte, so `pe_asm` refuses it
(it applies the clocked range to both forms — stricter than silicon, the safe
direction). The ranges are derived from the RTL decode
(`model/count_ranges.py`, anchors A6/A7), not typed.

⚠ **A host sees CONFIG_ERR and must assume the image, not one lane, is**
**suspect.** Reload before expecting anything else to run. The flag is
sticky and the engine does not resume on its own.

⭐ The refusal emits **no pin edges**: the drive arms are gated on the same
condition, so a refused action does not move a pin on its way to being
refused. `tb_pinrange +MODE=3` asserts exactly that, on both routes.

### How the flags clear, and what that costs you

**Reset only.** Every flag above is sticky until `rst_n`. There is no
clear-on-read. Stated plainly because it has a consequence a host must plan
around: **a single TX underrun makes the stream carry status frames in every
idle slot for the rest of the run.**

That is bounded rather than harmful, and the two reasons are worth knowing:

- **A payload always wins the next frame slot.** Self-started status is queued
  only when no RX payload is pending, so a set flag can never push data out of
  the stream — it fills slots the payload did not want.
- **An RX payload is held one deep.** `rx_push` from the engine is a one-cycle
  pulse, so before this a payload arriving mid-frame was simply *lost*; with a
  set sticky flag filling idle slots that would have meant dropped bytes rather
  than delay. A second pulse arriving while one is pending is a real overrun
  and sets **RX-drop**.

  ⚠ **The margin here is smaller than it was described as.** This used to read
  "two orders of margin: a frame takes 18 cycles and the fastest RX lane
  delivers a byte every 414". The frame figure was wrong twice over — a frame
  is **25 cycles** (12 bits at two clocks, plus one clock to queue the next)
  and a **payload slot is 50**, because a status frame always follows a payload
  one. And the comparison was against the wrong quantity: what binds a one-deep
  register is not a lane's average byte period but whether **two completions
  from different lanes land inside one 50-cycle slot**, which is a question
  about their relative phase. The two RX lanes' byte periods are 400 and 3312
  cycles, unrelated, so the phase drifts and a collision is reachable.

  ⇒ **What is guaranteed is that a collision is reported, not that it cannot
  happen.** `test/run_rxbw.py` measures both halves: forced over-rate, 3,405
  bytes dropped with **RX-drop set every time and never silently**, and every
  surviving byte delivered **in order** — so the register refuses the new byte
  rather than clobbering the pending one. A host that must not lose a byte
  should keep the aggregate completion rate below one per 50 cycles and read
  **RX-drop**.

⛔ **Status does not self-start on a timer.** An unconditional heartbeat would
queue a frame every 25 cycles — it would have paid for liveness with the data
it exists to report. Status self-starts only while a flag is set, which is what
makes it an error channel rather than a background load.

### The link's real capacity

| | |
| --- | --- |
| bit time | 2 clocks |
| frame | 12 bits + 1 queue clock = **25 clocks** |
| payload slot | **50 clocks** (a payload frame and the status frame after it) |
| payload capacity | **8.00 Mb/s** |
| shipped two RX lanes | 1.12 Mb/s = **14.0% utilised** |
| readback, one byte | 50 clocks (readback frames alternate with status too) |
| readback, full 256-byte store | 12,800 clocks = **256 µs** at 50 MHz |

⚠ **Readback got slower with the frame**, and it is worth stating because a
host that polls the store after every load pays it: a full walk was 194.6 µs at
9 bits and is **256 µs** at 12. That is the honest cost of the lane field —
readback frames carry `kind = 7` and gain nothing from it, but the frame could
not widen for payload alone (the marker arrives last, so both types must be the
same width).

⛔ **`1.6p` published "2.2% of the clock" and that was the raw pin rate** — one
bit per clock on the data pin, which the stream never runs at. It ignored the
two-clock bit time, the 4 non-payload bits per frame, the status frame that
always follows a payload, and the queue clock between frames. ⚠ The error
**predates** the 12-bit frame: at 9 bits the true figure was 10.6%, and the
widening moved it to 14.0% — the mis-stated capacity accounted for the other
4.8×. Both numbers are measured by `test/run_rxbw.py`, which reproduces the
50-clock slot at every point of a 12-point sweep and locates the loss boundary
where the same arithmetic predicts it.

## The readback contract

In **load mode** the payload frames carry the program store, so a host can
verify what it loaded. In **run mode** they carry RX payload.

1. **Readback starts at address 0, and the first payload frame IS byte 0.**
2. **The rewind trigger is `rst_n`.** Not entering load mode: the stream runs
   *concurrently* with loading, so by the time the last byte is written the walk
   is already past the image. The program store is deliberately **unreset**, so
   a reset rewinds the walk and keeps the image.
3. **The stream is only meaningful once the load is complete.** Reading it during
   the load returns whatever has been written so far, and the walk may pass
   addresses before the host writes them.
4. In a run the chip accepts there is no unloaded region: every image writes
   the whole store. The store is left uninitialised on purpose, so an address
   never written reads **X** in simulation and, on silicon, whatever the store
   powered up with; a load that stops short is refused rather than run.

⛔ **Points 1 and 2 are a ruling, not a description of an accident.** Byte 0 used
to be unreachable: the readback incremented its pointer in the same cycle it
requested a read, and the store was addressed from the incremented value, so
address 0 was never requested and the first frame carried a register from before
any read. Byte 0 is the first byte of lane 0's header — its `pin` and `clkpin`
fields — so the one byte a host could not verify was part of the descriptor
deciding which physical pin lane 0 drives.

The fix was two parts, and **the first alone was not enough**: latching the
pre-increment address made byte 0 reachable but it arrived *second*, behind one
stale frame, because a frame was still queued before its own read landed. The
readback now **primes** — its first two visits issue the read and let it land
without queueing a frame — so every frame carries the byte its own request
fetched. A pipeline's first output is not data.

## Supplying a payload byte — the TX nibble channel

| pin | run-mode use |
| --- | --- |
| `ui_in[4:1]` | TX payload nibble, **2 pushes per byte, HIGH nibble first** |
| `{ui_in[5], ui_in[0]}` | TX **queue tag** (0–3), latched with the HIGH nibble |
| `ui_in[6]` | TX payload **PUSH** (rising edge; it is `WR` in load mode) |

Push the high nibble, then the low nibble. The assembled byte enters one of
**four 2-deep queues**, chosen by the tag the host presented with the high
nibble. The engine pops a byte from a queue each time a `SHIFT` that names
that queue consumes data. `pe_asm` requires each queue to belong to one lane
(`check_queue_ownership`), so the tag says which lane a byte is for. The
nibble and tag are sampled on the synchronized `PUSH` edge and obey the hold
rule in [Input synchronization and host timing](#input-synchronization-and-host-timing).

⛔ This section used to say "one FIFO" and to omit the tag pins. The RTL has had
four tagged queues (`TXN = 4`, `TXD = 2`) since the tag was added, and
`info.yaml` listed `ui[0]` as unused; both are corrected (ruling CDC DOC).

- **`uio` carries protocol pins only.** Nothing of the data channel is spent on
  it, which is what lets the host feed a lane while a protocol is live.
- **A push on a full FIFO is reported, never stalled** — sticky **TX-full** in
  the status frame (bit 4). The host has no back-pressure pin, so a flag in the
  stream is the only honest answer, the same reasoning as RX overflow.
- **A lane that consumes with the FIFO empty records an underrun** (status
  bit 1). It is recorded per lane inside the chip but reported OR-ed across
  lanes, so the host learns that an underrun happened, not which lane (see
  *What is kept* under Reloading). Staging one byte ahead is what the FIFO is
  for.
- **Every byte a TX lane sends is a host byte, from the first** (silicon fix
  #8, WF2). A byte's first bit is taken from the queue head, and that is
  when the byte is **popped**; the remaining bits shift from the lane's
  register. If the queue is empty at a byte's first bit, the lane underruns
  and sends a zero byte, so the byte alignment is kept.
  ⛔ Before the fix a lane loaded its next byte at the END of each byte, so
  the first byte after every load was the register's reset value `0x00`: a
  UART peer received a NUL, an I²C program's first transaction addressed
  `0x00` (the General Call), an SPI FRAM's first WREN was no opcode at all.
  Programs had been written around it; those workarounds are removed.

### Push before the slot: the synchronizer window

A push crosses `ui_in[6]`'s synchronizer (a 2-flop rise detect), then the
queue register, before a lane can take it. So a byte is **guaranteed taken by
its slot only if its LOW-nibble PUSH edge reaches the pin at least 6 clock
cycles (120 ns at 50 MHz) before the slot's first bit appears on the
wire.**
- **Measured:** `test/run_v2window.py` shows the chip needs 5 cycles. The 6th
  covers an asynchronous host, whose edge can land anywhere within a cycle.
- **Pushed later than that:** the byte may go out in that slot, or the slot
  underruns (whole zeros, flagged) and the byte goes out whole in the next
  slot. Either way the byte is never mixed with another.
- This sits beside the PROG / PTR / data hold rules above. The benches must
  respect it too: V2 flags any slot whose byte was pushed inside the window
  as AMBIGUOUS (red), because the chip may legitimately go either way.

### Minimum host feed rate (the host contract for TX)

An underrun on a correctly fed program is a **host-contract violation**: the
lane shifts zeros the host did not send (an underrunning SHIFT shifts in 0s,
and a queue is not refilled retroactively). Correct feeding, per TX lane:

- **B, the lane's byte time.** The cycles between two consecutive byte loads
  on the lane: the sum of the delays of **every** action it runs per byte,
  framing included (a UART start and stop bit, an SPI chip-select). The
  shifting part alone is a lower bound, and using it is the safe direction
  (a smaller `B` is a stricter feed):
  - unclocked `SHIFT` with count `c` at delay `d`: `(c + 1) · d`;
  - clocked `SHIFT`: `(c + 1)` LOW + HIGH pairs, each `d + d_HIGH`
    (`d_HIGH = d`, or `d/2` on a HALF_HIGH lane; an open-drain HIGH also
    waits for the observed rise).
- **Rate:** on average, at least **one byte per `B` cycles** into that
  lane's queue.
- **Latency:** a byte is popped at its first bit, from a 2-deep queue, so
  **refill a queue within `B` cycles of each pop**. That leaves the one
  queued byte as the margin.
- **Channel capacity:** a byte is two PUSH edges. At the pacing the bench
  uses (`test/host_feed.vh`: 2 cycles setup, 3 high, 1 low per nibble), that
  is **12 cycles per byte**, shared by all four queues. So the lanes a host
  feeds together need `Σ 12 / B_q ≤ 1`.

Worked examples at 50 MHz:

| lane configuration | B | feed at least | refill within |
|---|---|---|---|
| UART-tx 115200 8N1: start + 8 data + stop at d = 434 | 4,340 cycles | 11.5 kB/s | 86.8 µs |
| SPI-tx 1 MHz, clocked `SHIFT` c = 7, d = 25 (push-pull), back-to-back bytes | 400 cycles | 125 kB/s | 8 µs |

✓ **Checked in simulation:** layer V3 in `test/clocked_conform.vh` fails any
underrun on a fed arm (`clocked_conform[V3-U]`). A bench that pushes nothing
by design declares `+V3_UNDERRUN=1`, and is then held to "no push, and every
load underran".

⛔ **This section previously described something else, and that was a real
defect rather than loose wording.** The RTL took `host_data` from `uio_q1` —
*eight bits of the protocol bus* — and pushed on `ui_in[0]`, while `ui_in[4:1]`
sat in the `_unused` concatenation and no FIFO existed at all. Both halves of
F1's ruled channel (`PHASE1_CLOSEOUT_PART3`) were unbuilt, and the consequence
was not cosmetic: **a host could not deliver a payload byte without driving the
very pins a live protocol was using.** That is why no program could address the
SPI FRAM, and therefore why no I²C ACK — and no peer-driven clock stretch — was
reachable. Fixed; this document now describes the ruling rather than the
deviation.

⚠ PART4 superseded the **RX** half of that table (three spare `uo_out` pins
cannot carry a nibble plus a valid, so RX went bit-serial — the serial host view
above), and PART5 framed status **into** the stream, which retires the
`ui_in[5]` pop and the `ui_in[0]` view select. Neither supersedes the TX nibble
or "zero `uio` spent".

## SPI-target timing (CS, MISO enable, first bit)

*Rulings CS1–CS3, silicon fix #6.* For an external SPI master talking to an
SPI-target lane (`uio[4]` SCK, `uio[5]` MOSI, `uio[6]` CS, `uio[7]` MISO), at
50 MHz:

| event | chip behaviour | time |
| --- | --- | --- |
| CS rises (deselect) | MISO **released immediately**: the enable flop is cleared asynchronously | gate delay only |
| CS falls (select) | MISO enable rises on the **3rd clock edge** after the fall: the enable's input is held at 0 until the `uio` synchronizer has seen CS low | 40–60 ns; ≤ 80 ns if the first synchronizer flop resolves late |
| CS falls → first MISO data bit on the pad | the lane is released by the synchronized CS edge, scheduled, dispatched, and its pin register drives the pad: `L_SYNC + (r − C) + OUT_REG (+ C)` from the reactive budget (`gate_admissibility_1_6`, 1.6 reactive) | ≤ **13 cycles = 260 ns** (10 cycles if the action drives at START) |

**What the master must allow:**

- **CS setup:** at least **14 cycles = 280 ns** from CS falling to its **first
  sampling SCK edge**. That's the 260 ns first-bit bound plus one cycle of
  master setup (`TSU_MASTER`).
- **SCK ≤ 1 MHz** (`SPI_TARGET_MAX_HZ`, gate 1.6k): every later bit has the
  same 13-cycle response budget against a half period of 25 cycles.
- **CS high time ≥ 3 cycles (60 ns):** the synchronizer must see the deselect
  before the next select. A shorter glitch could leave the enable's input
  armed when CS falls again, which is exactly the hazard fix #6 removes.

**Do common masters meet the setup?** At the 1 MHz limit, yes, by
construction. In every SPI mode the master's first *sampling* edge comes at
least half an SCK period after the clock starts: SCK idles, then the first
edge launches or samples, and the sampling edge is never the first
half-period. That's ≥ 500 ns ≥ 280 ns **even with zero CS lead**. The bound
would only bind above about 1.8 MHz with no CS lead, which is outside the
1 MHz limit anyway. The Pico SDK's examples drive CS as a software GPIO,
which only adds lead. ⚠ This is argued, not yet measured on the demo
board's master; it is on the FPGA bring-up checklist.

⛔ **Silicon fix #6.** The MISO enable used to be set on the first clock edge
after CS fell. The engine holds its MISO enable high between transactions,
so the asynchronous clear was released with the flop's input already 1, at
an arbitrary instant relative to the clock: a recovery hazard on the MISO pad
enable that neither simulation nor static timing sees. An earlier argument
that this was benign was refuted by its own bench check
(`test/inv_cdc.vh`, in every DUT bench) on the first CS fall it examined.
The input is now qualified by the synchronized CS, so a marginal release
resolves to 0 by construction. Must-fire: `M_CS_RAW_D`.

### Measured: the SPI-target witness (`test/run_spitgt.py`)

The program is `pe_proto.SPITarget`: one bit per SCK change-edge, all four
modes; images `test/sptgt_m{0,1,2,3}_image.hex` and `sptgt_mosi_image.hex`.
It runs against an SPI master on its own clock (`test/tb_spitgt.v`). These
are simulation numbers from a single lane, and they sit inside the analytic
bounds above, which remain the contract because they cover contention. The
1 MHz limit is A2's worst-case analysis; the multi-lane contention arm that
would measure it under load (B3b) has not run yet:

| quantity | measured | contract |
| --- | --- | --- |
| CS falls → MISO valid, bit 7 (modes 0/2) | 6 cycles = 120 ns | ≤ 13 cycles |
| SCK change-edge → MISO carries the new bit | 6–8 cycles = 120–160 ns | ≤ D_tol 17 cycles |
| ARM re-arms before the next change-edge, 1 MHz | ≥ 23 cycles of margin | — |
| ARM re-arms before the next change-edge, MOSI variant, 500 kHz | ≥ 34 cycles | — |

**CS hold (tCSH ≥ 0).** Keep CS low **through the master's final sampling
edge**. That is sufficient: the witness's `tCSH = 0` arm (CS rising at the
final sampling edge) reads every byte and passes the bit checker. CS rising
before that edge releases MISO under the master, which samples the pull-up
(must-fire M6: the master's byte and the chip's own V3 check both go red).

**The master samples a driven MISO only.** A released MISO reads as the
pull-up's 1, and that can match the data by luck. The witness fails any
sample of a released MISO on its own (must-fire M5: `tCSS = 2` cycles). It
first *passed* because the first fed byte had bit 7 = 1.

**Measured minimum CS lead: 6 cycles = 120 ns.** A sweep of the master's lead
from CS falling to its first SCK edge (the sampling edge in modes 0 and 2),
`TCSS` = 2 … 7 cycles at 1 MHz: 2–5 fail (MISO is still released at the
sampling edge), 6 and 7 pass, identically in modes 0 and 2. One master clock
phase was swept. The 280 ns setup above is the contract; 120 ns is what one
uncontended lane needs.

**Recovery after a short transaction.** The lane has no CS abort: it can't
wait on two pins at once. A transaction cut short (a missing SCK edge) leaves
it a bit out of step until **the host reloads the program**, using the
procedure in [Reloading a program](#reloading-a-program--a-reload-is-a-clean-slate).
A reload flushes the TX queues and resets the lane; the next byte MISO
carries is the first one pushed after PROG falls. Must-fires M3 (desync) and
M3R (exact again after the reload).

**Compared with a real SPI part.** Fujitsu MB85RS64V FRAM, datasheet
DS501-00015-4v0-E, p. 14 (AC characteristics): CS setup tCSU ≥ 10 ns, CS hold
tCSH ≥ 10 ns, output valid tODV ≤ 20 ns, deselect tD ≥ 60 ns, at up to 20 MHz.
This chip asks more of the master: a 280 ns CS setup and ~160 ns to valid
data, at 1 MHz. **Our target needs more CS setup than that FRAM**: 120 ns
measured and 280 ns contracted, against its 10 ns. A master tuned to the FRAM's
minimum would fail here. Typical masters provide the lead anyway: at 1 MHz
the first sampling edge comes ≥ 500 ns after the clock starts, even with zero
CS lead (see above). Our CS hold (≥ 0 through the final sampling edge) is
looser than the FRAM's 10 ns. The *form* of the requirement is the same one
a datasheet states, and the numbers are what a scheduled lane on a 50 MHz
engine delivers.

## SPI master receive timing (clocked SHIFTIN on a push-pull clock)

*Ruling CI2, silicon fix #3. Measured in `test/run_spidelay.py` (CI).*

**What the chip samples.** A clocked SHIFTIN reads the **action's** pin (MISO),
not the lane header's data pin (MOSI). On a **push-pull** clock it samples MISO
**as the MISO pad stood at the chip's own SCK pad rise**. It doesn't wait to
observe the rise: an SPI master's SCK sits on `uo_out`, which has no input path,
and a push-pull clock can't be stretched anyway. Open-drain clocks (I²C) still
sample on the **observed** rise, so a stretching target is read when it lets go.

**The instant, exactly.** The capture fires when `pin_in` shows the MISO pad as
it was at the SCK pad's rise. That's 2 cycles after the pad edge, the input
path's depth as measured from the pads. A `uo_out` SCK pad rises 2 cycles after
the HIGH-phase dispatch (one extra cycle behind its output register), so the
capture fires 4 cycles after that dispatch; a `uio` clock fires at 3. What
simulation doesn't model (the SCK output pad, the MISO input pad and board
flight time) is covered by the hold window below: one cycle of margin either
side of the sample edge.

**When MISO is sampled.** The chip samples MISO on a single system-clock edge,
one cycle after the edge that launches SCK high. This was measured identically
on both RTLs by flipping MISO for one cycle at each offset: only that edge
corrupts the read. The peer must hold MISO stable **from the SCK rise until
40 ns (2 cycles at 50 MHz) after it**, at the chip's pins. That allows one cycle
of margin on either side of the sample edge, assuming total pad and board delay
below 20 ns.

**How short an SCK phase can be.** Each SCK phase lasts `d` cycles nominally. A
late dispatch shortens it, high or low, because both phases are dispatch gaps:

**shortest phase ≥ d − (r_i − C)**, with C = 3 and r_i the lane's worst-case
response from **A2's response-time analysis for this program**.

r_i depends on the whole program, other lanes included.
- ⚠ `pe_asm` computes r_i for every lane (its condition 1.6a check) but doesn't
  report it for SPI lanes. A host gets its own figure from
  `program_a2.lane_responses(image, pyrta_src)`.

- **Admissible programs** (every delay ≥ D* = 20, and an A2 bound exists): the
  floor above is the guarantee.
  - For the **shipped 1 MHz lane** (d = 25, r_i = 12): **16 cycles = 320 ns**.
  - Measured on a five-lane admissible image (the A2 reference workload's
    closest buildable equivalent, with reactive lanes modelled as self-timed
    periodic lanes at the same rate) under an adversarial phase sweep:
    - the lateness bound was reached exactly (9 of 9);
    - the shortest observed phase was 17 cycles, so the 16-cycle floor holds,
      with one cycle not exercised.
- **Programs below the floor** (non-admissible, such as the d = 7 trace image
  `corpus_spim`): no phase guarantee. The half-period shrinks by the
  scheduler's lateness, measured here as 7 cycles down to 5.

**Against the MB85RS64V** (RAMXEED DS501-00015-6v1-E, AC characteristics p. 12;
test conditions p. 13: VDD 3.0–5.5 V, 30 pF load, judged at VDD/2):

| parameter | symbol | datasheet | requirement | shipped 1 MHz lane |
|---|---|---|---|---|
| output data valid time | tODV | max 20 ns after SCK fall | MISO valid by the SCK rise: ≤ shortest low phase | budget **320 ns**: 300 ns left for board flight time |
| output hold time | tOH | min 0 ns | MISO changes only at the next fall, ≥ shortest high phase after the rise | shortest high phase 16 cycles; the hold window is 40 ns |
| clock high / low time | tCH / tCL | min 25 ns each | shortest phase ≥ 25 ns | 320 ns |

**Measured (CI3, `test/run_spidelay.py`, d = 7, non-admissible).** The peer
delays MISO by N cycles after each SCK fall:
- every read is correct for N ≤ 5;
- every read is wrong for N ≥ 8;
- N = 6 and 7 form a band.

A bit is read wrong exactly when its low phase is at most N − 1 cycles and the
MISO pad changes late. All 336 data bits were checked at N = 6 and 7, and no
bit with a full 7-cycle low phase failed.

## Lane mode bits (header bits 0–1: `HALF_HIGH`, `CLK_INV`)

The header's 4-bit field that used to hold a stale `C` value is now per-lane
mode bits. Bits 2–3 are reserved and must be 0; `pe_asm` and the image audit
refuse an image that sets them. Every image built before the change writes 0,
so it runs exactly as before.

### `HALF_HIGH` (bit 0): I²C Fm up to ~394 kHz

A clocked lane's HIGH phase lasts `d/2` instead of `d`; the LOW phase is still
`d`. On an open-drain clock the `d/2` counts from the *observed* rise, so
clock stretching works exactly as before.

- **The claim:** I²C Fm up to about 394 kHz with ideal edges. The delivered
  rate depends on the pull-up rise time, because the HIGH phase counts from
  when the chip sees SCL high. I²C modes are maxima, so a slower rate is still
  compliant.
- **Measured** (`run_ckack`, the part's random read at `d = 82`, decoded by
  sigrok): SCL period 127 cycles = 393.7 kHz at 50 MHz, HIGH 45, LOW 82. The
  minimum t_HIGH (45 cycles) and t_LOW (80) clear Fm's 30 and 65.
- **The toolchain refuses** `HALF_HIGH` when any clocked action has
  `d/2 < D* = 20`: the HIGH phase is a dispatch gap, and J = 1 holds only for
  gaps of at least `D*`. Fm+ does not need it; it already runs at 725 kHz.

### `CLK_INV` (bit 1): SPI modes 1 and 2

The lane's clock pin is driven inverted. A mode-3 program becomes mode 1; a
mode-0 program (SCK parked low before each select) becomes mode 2. The chip
still samples on its own HIGH phase, which on an inverted pin is the falling
edge, the edge modes 1 and 2 sample on.

- **Push-pull lanes with a `uo_out` clock only.** The inversion is applied
  just before `uo_out`'s output register, so every output bit is still a
  flop. A `uio` clock or an open-drain lane with `CLK_INV` is refused.
- **⚠ The idle level flips once, at header load.** After reset every
  protocol output idles high. When the header loads, an inverted SCK goes to
  its inverted idle level (low for a mode-1 program). Headers load before any
  action runs, so CS is still deasserted and the peer ignores the edge. This
  is checked on the pins: the first SCK edge after reset happens with CS high,
  and no SCK edge occurs while CS is asserted other than the transaction's
  own clock phases.
- **After a deselect or reset,** the same applies: the program reloads, the
  header sets the inversion, and only then do actions run.
- **Measured** (`run_spifram`, WREN / WRITE / READ, decoded by sigrok with
  each mode's CPOL/CPHA): mode 1 (39 reads) and mode 2 (38 reads), chip RX ==
  sigrok MISO == the written `5B C4`. The peer for these arms is our mode 0/3
  model behind an SCK inverter, because the MB85RS64V itself supports only
  modes 0 and 3.
