# Host interface — pins, load protocol, serial framing, readback contract

The host-facing spec. `PHASE1_CLOSEOUT_PART5.md` flagged that "the serial format
becomes host-facing spec: framing, bit order, and what happens when the host
stops reading" — this is that document, and it now also carries the **readback
contract** ruled after the byte-0 defect.

Everything here is observable at the pins. Nothing requires reading internal
state, which is what lets the same suite run against the gate-level netlist.

## Pins

`uio` carries everything that must be able to **stop driving** (inputs,
open-drain, tri-state); `uo_out` carries push-pull only. Both banks are exactly
full. The map is generated by `test/corpus.py` into `test/pinmap.vh` and checked
against `src/project.v`'s `MISO_PIN`/`CS_PIN` at generation time.

| pin | bank | lane | signal | class |
| --- | --- | --- | --- | --- |
| 0 | `uio[0]` | SPI-master | MISO | input |
| 1 | `uio[1]` | I²C | SCL | open-drain |
| 2 | `uio[2]` | I²C | SDA | open-drain |
| 3 | `uio[3]` | UART-rx | RX | input |
| 4 | `uio[4]` | SPI-target | SCLK | input |
| 5 | `uio[5]` | SPI-target | MOSI | input |
| 6 | `uio[6]` | SPI-target | CS | input |
| 7 | `uio[7]` | SPI-target | MISO | tri-state out |
| 8 | `uo_out[0]` | UART-tx | TX | push-pull |
| 9–11 | `uo_out[1:3]` | SPI-master | SCLK, MOSI, CS | push-pull |

`uo_out[6:4]` is the serial host view; `uo_out[7]` is spare and reads 0.

**Open-drain pins never drive a 1.** A pin's drive class follows the lane that
owns it (both its data pin and its clock pin), is fixed when the lane's header
loads, and is enforced at the output flop's D input — so an open-drain pin
driving high is unsatisfiable regardless of which opcode writes it. Low is
`oe = 1, out = 0`; the high phase is a **release** (`oe = 0`) and the line is
brought up by the bus pull-up, which is what makes an external device able to
hold SCL low and stretch the clock.

### Control inputs

| pin | name | meaning |
| --- | --- | --- |
| `ui_in[7]` | `prog` | 1 = load mode, 0 = run |
| `ui_in[6]` | `wr` / `push` | load: write strobe. run: TX payload PUSH. **Asynchronous** either way |
| `ui_in[5]` | `ptr` | load-pointer reset |
| `ui_in[4:1]` | `tx_nibble` | TX payload nibble, 2 pushes per byte (run mode) |

`wr` is treated as an asynchronous pin strobe: two flops to resolve
metastability and a third to see the edge. **Hold it for at least 3 clocks**, and
leave at least 3 clocks between writes.

## Loading a program

1. Assert `prog`.
2. Pulse `ptr` to reset the load pointer to 0.
3. For each byte: drive it on `uio[7:0]`, hold ≥3 clocks, raise `wr` for ≥3
   clocks, lower it, wait ≥3 clocks. The pointer auto-increments — there is no
   address bus.
4. Deassert `prog` to run.

Every `uio` pin is an **input** for the whole of load mode, which is what lets
the 8 protocol pins double as the load data port at zero pin cost. The 4
push-pull protocol outputs are held at **idle high** throughout, because
`uo_out` cannot release and an idling low could look like a START condition or a
clock edge to an attached device.

## The serial host view (`uo_out[6:4]`)

| bit | name |
| --- | --- |
| `uo_out[4]` | `data` |
| `uo_out[5]` | `strobe` |
| `uo_out[6]` | `valid` |

- `valid` is high for the whole of a frame and low between frames, so **its
  rising edge is the frame boundary**. Frame on that, not on a fixed stride.
- A frame is **9 strobed bits**: 8 payload bits **LSB first**, then a **marker**
  bit — `1` = status, `0` = payload.
- One bit per two clocks; `strobe` is high for one clock per bit. Sample `data`
  while `strobe` is high.
- Payload and status frames **alternate**, so liveness is in the stream even
  when no payload is moving.

### The status byte

| bit | meaning |
| --- | --- |
| 0 | always 1 — alive |
| 1 | TX underrun (sticky) |
| 2 | RX overflow (sticky) |
| 3 | `ovr` (sticky) |
| 7:4 | 0 |

**Overflow is reported in the stream, never as a stall**, because a host that
has stopped reading cannot be told by a pin it is not reading. The flags are
sticky.

## The readback contract

In **load mode** the payload frames carry the program store, so a host can
verify what it loaded. In **run mode** they carry RX payload.

1. **Readback starts at address 0, and the first payload frame IS byte 0.**
2. **The rewind trigger is `rst_n`.** Not entering load mode: the stream runs
   *concurrently* with loading, so by the time the last byte is written the walk
   is already past the image. The program store is deliberately **unreset**, so
   a reset rewinds the walk and keeps the image.
3. **The stream is only meaningful once the load is complete.** Reading it during
   the load returns whatever has been written so far, and the walk may pass
   addresses before the host writes them.
4. Reading past the loaded region returns **X**, not 0 — the store is left
   uninitialised on purpose, so a program that reads past its end looks wrong
   rather than plausible.

⛔ **Points 1 and 2 are a ruling, not a description of an accident.** Byte 0 used
to be unreachable: the readback incremented its pointer in the same cycle it
requested a read, and the store was addressed from the incremented value, so
address 0 was never requested and the first frame carried a register from before
any read. Byte 0 is the first byte of lane 0's header — its `pin` and `clkpin`
fields — so the one byte a host could not verify was part of the descriptor
deciding which physical pin lane 0 drives.

The fix was two parts, and **the first alone was not enough**: latching the
pre-increment address made byte 0 reachable but it arrived *second*, behind one
stale frame, because a frame was still queued before its own read landed. The
readback now **primes** — its first two visits issue the read and let it land
without queueing a frame — so every frame carries the byte its own request
fetched. A pipeline's first output is not data.

## Supplying a payload byte — the TX nibble channel

| pin | run-mode use |
| --- | --- |
| `ui_in[4:1]` | TX payload nibble, **2 pushes per byte, HIGH nibble first** |
| `ui_in[6]` | TX payload **PUSH** (rising edge; it is `WR` in load mode) |

Push the high nibble, then the low nibble. The assembled byte enters a **2-deep
FIFO**; the engine pops one byte each time a lane's `SHIFT` consumes data. There
is **one** FIFO, not one per lane: the shift action already names its lane, so
the host pushes bytes and the program does the routing — the same trick that
deleted the address bus.

- **`uio` carries protocol pins only.** Nothing of the data channel is spent on
  it, which is what lets the host feed a lane while a protocol is live.
- **A push on a full FIFO is reported, never stalled** — sticky **TX-full** in
  the status frame (bit 4). The host has no back-pressure pin, so a flag in the
  stream is the only honest answer, the same reasoning as RX overflow.
- **A lane that consumes with the FIFO empty records an underrun** (status
  bit 1), per lane. Staging one byte ahead is what the FIFO is for.

⛔ **This section previously described something else, and that was a real
defect rather than loose wording.** The RTL took `host_data` from `uio_q1` —
*eight bits of the protocol bus* — and pushed on `ui_in[0]`, while `ui_in[4:1]`
sat in the `_unused` concatenation and no FIFO existed at all. Both halves of
F1's ruled channel (`PHASE1_CLOSEOUT_PART3`) were unbuilt, and the consequence
was not cosmetic: **a host could not deliver a payload byte without driving the
very pins a live protocol was using.** That is why no program could address the
SPI FRAM, and therefore why no I²C ACK — and no peer-driven clock stretch — was
reachable. Fixed; this document now describes the ruling rather than the
deviation.

⚠ PART4 superseded the **RX** half of that table (three spare `uo_out` pins
cannot carry a nibble plus a valid, so RX went bit-serial — the serial host view
above), and PART5 framed status **into** the stream, which retires the
`ui_in[5]` pop and the `ui_in[0]` view select. Neither supersedes the TX nibble
or "zero `uio` spent".
